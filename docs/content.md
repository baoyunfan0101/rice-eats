# Content guide

Reference for the restaurant database: where it lives, its formats, how photos
and reviews are handled, and how drafts become public. Contributors do not need
to read this; they send text and/or photos, and a maintainer (usually with the
`restaurant-intake` Agent Skill) turns them into database records.

## Layers

- **Database** (`content/`): the canonical, file-based source of truth.
- **Content management** (`scripts/content/`, `.claude/skills/restaurant-intake/`):
  local commands and the Agent Skill that create, check, and approve records.
- **Website** (`src/`): reads data generated at build time
  (`public/generated/`, not committed) and never changes the database.

Code follows the same split. `shared/content/` is the framework-independent
data contract: `schema.ts` (canonical formats and validation),
`vocabulary.ts` (the only list of cuisine, tag, rating, and verdict keys), and
`model.ts` (the generated data the website reads). Content management
(`scripts/`) and the website (`src/`) both import `shared/`, never each other,
and `shared/` imports neither; `tests/unit/architecture.test.ts` checks this.
Display labels live only in the website (`src/lib/labels.ts`).

## Layout and privacy

The GitHub repository is public and anything committed stays in its history,
so unapproved material never enters Git:

```text
content/                          public database (tracked)
  contributors.json               public contributor identities: [{ "id", "name" }]
  tags.json                       public tag registry: [{ "id", "label", "aliases"? }]
  restaurants/<id>/               one folder per restaurant, named after its id
    info.json                     the restaurant's facts and dishes (Restaurant Schema below)
    reviews/<contributor id>.json one contributor's review: date, rating, dish verdicts, photos
    reviews/<contributor id>.md   optional; that review's text
    images/01-<name>.jpg          standardized photos; the first is the cover
private/                          git-ignored, never committed or deployed
  submissions/                    raw submissions while they are processed
    tally-<submission id>/        a Tally submission: submission.json, photos.json, photo-NN.*,
                                  and from prepare: prepare.json, resolutions.json, review-report.md
    tally-log.json                imported Tally submission ids and their status
  drafts/<id>/                    drafts, same layout as content/restaurants/<id>/
  contributors.json               new contributors and contact details
  tags.json                       proposed tags and keyword aliases learned from submissions
  cache/                          map listing lookups and fetched evidence pages
fixtures/                         fictional development data (never deployed)
```

There is no index to maintain: the build discovers every folder.
`npm run check:privacy` (also in CI) fails if anything under `private/` is
tracked or a tracked image carries metadata.

## Restaurant Schema (`info.json`)

Only `id`, `status`, and `name` are required.
Everything else is optional and is left out when the submission does not
provide it. Unknown fields are
rejected so typos are caught.

| Field            | Type / values                                  | Notes                                                                                                                                                   |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`             | e.g. `r-7k3m9q`                                | Required. Generated by `content:new`, unique, never changes (also used in URLs `/r/<id>/`). Must equal the folder name. Names may repeat.               |
| `status`         | `"draft"` or `"published"`                     | Required. Only `published` restaurants are built into the site; private drafts stay `draft`.                                                            |
| `name`           | string                                         | Required. The primary display name, in whatever language the restaurant is best known by (Chinese, English, or a bilingual sign). Can change freely.    |
| `altNames`       | string[]                                       | Other names: the name in another language, abbreviations, former names. Shown under the name and searchable. No duplicates of `name`.                   |
| `address`        | string                                         |                                                                                                                                                         |
| `location`       | `{ "lat": number, "lng": number }`             | Needed for the map. Must be within 100 km of Rice University.                                                                                           |
| `cuisines`       | cuisine keys, e.g. `["sichuan"]`               | Keys from `shared/content/vocabulary.ts`. Filterable.                                                                                                   |
| `tags`           | tag ids, e.g. `["date", "group"]`              | Ids from the [tag registry](#tags) (`content/tags.json`). Filterable. Only when the contributor said so.                                                |
| `pricePerPerson` | number (USD)                                   | Drives the price filter.                                                                                                                                |
| `dishes`         | `{ id, name, altNames? }[]`                    | The restaurant's dishes, which reviews rate by `id` (a slug such as `d1`, unique within the restaurant, never changes). `altNames`: other names for it. |
| `links`          | `{ googleMaps?, appleMaps?, website? }` (URLs) | Map links use the coordinates first, then the address; set them only to override a wrong result.                                                        |

The zod definitions are in `shared/content/schema.ts`; the generated shapes the
website reads are in `shared/content/model.ts`.

### Controlled values and labels

Data stores keys from `shared/content/vocabulary.ts`; display labels are
defined only in `src/lib/labels.ts`, so wording can change without touching
restaurant data. To add a cuisine, add its key to `vocabulary.ts` and its label
to `labels.ts` (type checking reports a missing label). Tags are open-ended and
live in their own registry instead (next section).

### Tags

`content/tags.json` lists every public tag: a stable `id` (a lowercase slug,
used in data and in `?tag=` URLs, never renamed), its display `label`, and
optional `aliases` (other words for it). Ids, labels, and aliases must not
collide; `content:check` rejects a restaurant tag that is not in the registry.

Contributors type free-form keywords in the submission form (the
`标签（选填）` question, separated by commas or "、"). `content:submission -- prepare` maps each keyword to a tag by id, label,
or alias, then by aliases learned from earlier reviewed submissions; other
keywords wait for a reviewed decision in the submission's `resolutions.json`
(reuse a tag, create a new one, or skip). New tags are proposed privately in
`private/tags.json` and a draft may use them; `content:promote` copies their id
and label (never the contributor's words) into `content/tags.json`. To rename a
label, edit `content/tags.json`; to add a tag by hand, append it there. Tag
words appear on every restaurant that uses them, so they must not carry
contact details; the checks are described in
[submissions.md](submissions.md#keywords-and-tags).

| `rating` | Label     |     | `verdict` | Label   |
| -------- | --------- | --- | --------- | ------- |
| 5        | 🥵 夯     |     | 1         | 🔥 推荐 |
| 4        | 😘 顶级   |     | -1        | 💣 避雷 |
| 3        | 🤤 人上人 |     | (absent)  | none    |
| 2        | 🫤 NPC    |     |           |         |
| 1        | 🤮 拉完了 |     |           |         |

The overall rating is not stored: the build averages the ratings of every
review (one decimal, shown with the label of the nearest level and the number
of reviewers). Sorting by rating uses that average; a draft without reviews
sorts last.

Example:

```json
{
  "id": "r-7k3m9q",
  "status": "draft",
  "name": "示例拉面",
  "altNames": ["Example Noodles"],
  "cuisines": ["japanese", "ramen"],
  "tags": ["solo"],
  "location": { "lat": 29.7166, "lng": -95.4137 },
  "pricePerPerson": 18,
  "dishes": [
    { "id": "d1", "name": "豚骨拉面", "altNames": ["Tonkotsu"] },
    { "id": "d2", "name": "煎饺" }
  ]
}
```

## Reviews (`reviews/`)

A restaurant has one review per contributor, each in
`reviews/<contributor id>.json` with an optional `reviews/<contributor id>.md`.
The file name is the credit: public names come from `content/contributors.json`.
A later submission by the same contributor updates their review instead of
adding another. A published restaurant needs at least one review.

| Field    | Type / values                             | Notes                                                                                                                         |
| -------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `date`   | `"YYYY-MM-DD"`                            | Required. When it was submitted (or last updated); reviews are shown newest first.                                            |
| `rating` | integer `1`-`5`                           | Required. This contributor's rating (labels above).                                                                           |
| `images` | `["images/<file>", ...]`                  | Photos of the restaurant (not of one dish), in display order.                                                                 |
| `dishes` | `{ dish, verdict?, comment?, images? }[]` | `dish`: an id from `info.json` `dishes` (each at most once). `verdict`: `1` 推荐, `-1` 避雷, absent = no opinion. Its photos. |

```json
{
  "date": "2026-10-14",
  "rating": 4,
  "images": ["images/01-storefront.jpg"],
  "dishes": [
    { "dish": "d1", "verdict": 1, "comment": "汤很浓", "images": ["images/02-ramen.jpg"] },
    { "dish": "d2", "verdict": -1 }
  ]
}
```

Every photo in `images/` belongs to at most one review; `content:check` reports
a photo used by two reviews, an unknown dish id, and a dish no review rates.

## Contributors

`content/contributors.json` lists public identities only (`id`, `name`).
New contributors and contact details (email or another contact method) are kept
in `private/contributors.json`; a contributor's display name is copied to the
public list when a restaurant crediting them is promoted. Contact details never
reach Git, the build, or the website (the build output is checked for them).

## Review text (`reviews/<contributor id>.md`)

Optional Markdown (GitHub flavor) with no required structure. Leave it out
when there is no written content.

- Photos are listed in the review's `.json`, never in the text (an image in the
  text is an error).
- Headings are shifted below the page's section headings (`#` becomes a
  level-3 heading).
- Raw HTML, scripts, and unsafe links are removed at build time.

## Photos

`npm run content:add-images -- <id> <files...>` stores standardized copies and
never changes the originals: numbered `NN-<name>.jpg` (PNG only for
transparency), upright, at most 2400 px, and without EXIF/XMP/IPTC metadata
(GPS, camera, time). New photos get the next number, so the first image (the
cover, with the restaurant name as alt text) stays the same. HEIC/HEIF needs
macOS `sips` or `heif-convert`.

The database accepts nothing else in `images/`: wrong names, oversized images,
non-JPEG/PNG content, or embedded metadata are blocking errors in
`content:check`, the build, and `check:privacy`.

On a restaurant page every stored photo is reachable
(`src/lib/imagePlacement.ts`):

1. **Cover**: the first image is shown at the top.
2. **Dish cards**: a dish shows the photos of every review that rates it, with
   its 推荐 and 避雷 counts: one large photo, and with several, numbered
   thumbnails to switch between them (buttons; the arrow keys move between
   them). Its panel (`#dish-<id>`, a shareable link) lists every reviewer's
   verdict, comment, and photos, newest first.
3. **Reviews**: every review, newest first, starts with its reviewer's rating,
   name, and date, then its text, dish verdicts, and its own photos.
4. **照片 gallery**: photos no review uses (added by the maintainer), in
   stored order.

So photo-only restaurants show the cover and then every other photo, and no
display flags are stored in the data. List cards and map previews always use
the cover. The build turns
each photo into WebP renditions 480, 960, and 1600 px wide (never upscaled,
metadata-free), cached in `.cache/images/` by content hash.

## From submission to website

Contributors send material to a maintainer directly or through the public
Tally form on the website; [docs/submissions.md](submissions.md) describes the
form, the Gmail notifications, and `npm run content:submission`, which brings
Tally submissions into `private/submissions/` before the steps below. A
submission about a restaurant that already has reviews adds the contributor's
review (or updates their earlier one); other reviews are never changed.

1. **Prepare** a private draft. For a Tally submission,
   `npm run content:submission -- prepare <submission id>` builds it (see
   docs/submissions.md). By hand: `content:new` or `content:edit`,
   `content:contributor`, `content:add-images`, edit `info.json` and
   the contributor's `reviews/<contributor id>.json` (and `.md`), then `content:check -- <id>`. Preview with
   `npm run dev:drafts`. Problems in drafts are warnings and never block builds.
2. **Review** the content and the contributor's permission and attribution.
3. **Add to the database**: `npm run content:promote -- <id>` lists what would
   become public (or the file changes for an edit); with `--approved` it moves
   the folder into `content/restaurants/<id>/` and publishes new contributor
   names and new tags. A new restaurant stays `"status": "draft"`; an edit keeps the public
   status. Commit it.
4. **Publish**: `npm run content:publish -- <id> --approved` re-validates and
   sets `"status": "published"`. The site updates when the change reaches `main`.

Steps 3 and 4 are maintainer decisions. The `--approved` flag only prevents
accidental runs; the tools cannot verify who approved, and passing validation
is never approval.

Errors in published content fail `npm run build`. After `vite build`,
`scripts/postbuild.ts` checks `dist/` against an allowlist (Vite's build
manifest, `PUBLIC_STATIC_FILES`, and the generated data and WebP images of
published restaurants), rejects private contact details, and fails on anything
else.

## Commands

| Command                                                       | What it does                                                                    |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `npm run content:new -- --name <name>`                        | Create a private draft with a new id; add other names to `altNames`.            |
| `npm run content:edit -- <id>`                                | Copy a public restaurant into `private/drafts/` to change it.                   |
| `npm run content:contributor -- find <name or email>`         | Find existing contributors to reuse their ids.                                  |
| `npm run content:contributor -- add --name <n> [--email <e>]` | Register a contributor privately.                                               |
| `npm run content:add-images -- <id> <files...>`               | Store standardized photo copies.                                                |
| `npm run content:extract -- <file>`                           | Print text from `.txt`, `.md`, `.docx`, `.doc`, `.rtf`, `.odt`, `.html`.        |
| `npm run content:submission -- import <csv or json>`          | Import Tally submissions privately (see docs/submissions.md).                   |
| `npm run content:submission -- status`/`retry-photos <id>`    | Check a submission; retry its missing photos (also `add-photo`, `waive-photo`). |
| `npm run content:submission -- prepare <id>`                  | Build or update the private draft from a submission, with a review report.      |
| `npm run content:submission -- fetch-page <url>`              | Save a public page's text privately as evidence for restaurant information.     |
| `npm run content:submission -- list` / `mark <id> --status …` | Show or update the private log of imported submissions.                         |
| `npm run content:check [-- <id>...]`                          | Validate drafts and the database; list ids, names, missing information.         |
| `npm run images [-- <id>...]`                                 | Process photos and print the renditions.                                        |
| `npm run content:promote -- <id> [--approved]`                | Move an approved draft into the public database.                                |
| `npm run content:publish -- <id> [--approved]`                | Show a restaurant on the website.                                               |
| `npm run content:build`                                       | Write site data to `public/generated/` (part of `build`).                       |
| `npm run check:privacy`                                       | Check tracked files for private material and image metadata.                    |

Add `--source fixtures` to `content:check`, `content:build`, or `images` to
work with the fictional fixtures.
